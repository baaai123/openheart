# ADR-0001: 用户模型隐私边界

**日期**: 2026-05-14  
**状态**: 已采纳  
**涉及模块**: 记忆层(§3.4), 人格层(§4), 决策层(§5), 用户模型修正(§5.7.5)

## 背景

OpenHeart 的用户模型 (`UserModel`) 包含 5 类字段：`personality`(性格)、`communication_style`(沟通风格)、`emotional_pattern`(情绪模式)、`topics_of_interest`(兴趣话题)、`key_memories`(关键记忆)。

规范 §3.4 定义了这些字段的数据结构，规范 §5.1 规定"涉及个人敏感信息的记忆默认不写入冷记忆"。但规范未区分哪些字段属于敏感信息、哪些字段可以通过自动推断收集——留下了隐私边界的设计空白。如果不做显式决策，所有字段将默认采用同一收集策略，可能导致隐私越界或用户体验僵化。

## 决策

采用**分层收集策略**，根据字段性质区分自动推断与用户主动授权：

| 字段 | 收集方式 | 用户可修正？ | 机制 |
|---|---|---|---|
| `topics_of_interest` | 自动推断（对话主题频率统计） | ✅ "别聊电影了"删除 | 带 `model_confidence` |
| `communication_style` | 自动推断（句长、emoji 频率等统计特征） | ✅ "我不是那种正式的人"修正 | 带 `model_confidence` |
| `emotional_pattern` | 自动推断（多轮情绪标签统计） | ✅ **必须可修正**，触发 corrector | 带 `model_confidence` |
| `personality` | 自动推断（对话行为模式） | ✅ "别把我想得那么脆弱"修正 | 带 `model_confidence` |
| `key_memories` | **仅 opt-in**（"记住这个"触发） | ✅ "忘掉那个"删除 | 用户显式触发 |

**核心规则**：
1. 自动推断字段均附带 `model_confidence`（浮点数，0.0–1.0）
2. 所有字段均可通过 `user_model_corrector` 以自然语言修正
3. 用户修正后标记 `user_verified=true`，**自动推断不再覆盖**该字段的修正值
4. 用户修正的逆操作（如"我又喜欢电影了"）可清除 `user_verified` 标记，恢复自动推断

## 理由

- **`key_memories` 不全自动**：该字段记录具体生活事件（"上周去了海边"、"孩子叫小明"），自动推断等于监视感，违反"伙伴"产品定位
- **`topics_of_interest` 和 `communication_style` 不全 opt-in**：这两个字段是自然涌现的统计特征——如同朋友能自然感知你的喜好，不需要每次显式声明
- **`emotional_pattern` 强制开放修正**：情绪推断本质上是概率性的（基于 `emotion.category` 的 `joy`/`sadness`/`neutral` 统计），错误推论会造成实际困扰；修正接口是不可或缺的安全阀
- **`personality` 修正优先级最高**："别把我想得那么脆弱"不是偏好调整——是对事实判断的纠正。机器推断必须让位于用户自我认知
- **修正优先于推断**：用户修正代表 ground truth。自动推断可能因数据偏差或上下文不足产生错误，用户修正必须具有最终决定权

## 后果

### 正面
- 用户对哪些信息被收集有清晰预期，隐私安全感增强
- 自动推断降低用户上手成本，无需主动填写画像
- 自然语言修正界面降低交互摩擦——用户不需要学习配置界面

### 负面（需接受）
- **不可逆性**：一旦自动推断开始运行，系统对用户的"感知"就逐渐形成。虽然修正可以调整值，但无法完全抹去系统已学到的模式——模型权重和冷记忆缓存可能存在残留
- **实现复杂度**：`user_model_generator` 必须为每个推断字段附加 `model_confidence`；`user_model_corrector` 必须能解析自然语言修正意图（意图分类 + 实体提取 + 值更新）；所有下游消费者必须检查 `user_verified` 标志决定是否采纳
- **误判风险**：自动推断可能在用户不活跃期产生低质量画像（冷启动阶段），需要设计置信度阈值避免早期低质量推断影响决策

### 实现要求
- `user_model_generator` 输出格式必须包含 `{ field, value, model_confidence, user_verified }`
- `user_model_corrector` 输入为自然语言，输出为结构化的字段修正指令
- 所有读取 `UserModel` 的下游模块（人格层、决策层、主动话题等）必须检查 `user_verified`：
  - `user_verified=true` → 使用用户修正值，忽略自动推断
  - `user_verified=false` → 使用自动推断值（带置信度阈值过滤）
- 冷启动阶段（用户交互 < 50 轮）：自动推断置信度降低 30%，避免过早固化画像

### 测试要求
- 合约测试必须覆盖以下场景：
  1. 自动推断 → 字段填充 + `model_confidence` 附加
  2. 用户修正 → `user_verified=true` + 值变更
  3. 用户修正后自动推断重跑 → 值不覆盖
  4. 用户撤销修正 → `user_verified` 清除 + 恢复自动推断
  5. 冷启动置信度惩罚
  6. `key_memories` 未经 opt-in 不得写入

## 备选方案

### A: 全部自动推断
最简实现——所有 5 个字段均由系统自动推断填充，用户无修正接口。
- **优点**：工程实现最简单，系统从第一天就有完整用户画像
- **缺点**：`key_memories` 自动推断越过隐私舒适区，用户感到被监视；`emotional_pattern` 错误无法修正会累积负面体验
- **结论**：否决。违反"伙伴"定位，隐私风险不可接受

### B: 全部仅 opt-in
所有 5 个字段都需要用户主动触发或确认才开始收集。
- **优点**：隐私最安全，零自动收集
- **缺点**：使用摩擦过大，系统长期缺乏用户认知——用户交互数百轮后模型仍为空；主动话题、预防性安抚等功能依赖用户画像，全部 opt-in 导致这些功能形同虚设
- **结论**：否决。导致核心功能不可用

### C: 纯正则过滤
不区分字段类型，仅用正则匹配（身份证号、手机号等模式）过滤敏感信息，其余全部自动收集。
- **优点**：实现简单，容易审计
- **缺点**：仅捕获结构化 PII（身份证、手机号），无法识别自然语言中的隐私信息（如"我上周去了海边"、"我讨厌 XXX同事"）；隐私保护覆盖率低
- **结论**：否决。隐私覆盖范围不足，虚假安全感
