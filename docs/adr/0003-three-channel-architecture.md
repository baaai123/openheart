# ADR-0003: Three-Channel Architecture (VLM → LLM → IconCache)

**日期**: 2026-05-17  
**状态**: 已采纳  
**涉及模块**: 感知层(§2), 融合层(§3), 决策层(§5), 执行层(§7), IconCache, 鼠标控制

## 背景

OpenHeart 的视觉感知管道最初采用"全注入"策略：将 OCR 文本、OmniParser 的 UI 元素检测结果、YOLO 目标检测框等所有结构化视觉数据直接拼入 LLM prompt。实践中暴露出两个严重问题：

1. **终端噪声** — OCR 可能从桌面图标、后台窗口、系统托盘等非焦点区域抓取无关文本。LLM 收到大量与当前交互无关的视觉 token，增加了幻觉风险。
2. **Token 膨胀** — OmniParser 输出的结构化 UI 树单帧可达 200-400 个元素。直接注入 LLM prompt 使视觉描述部分从约 100 tokens 膨胀到 400-800 tokens，显著增加 API 调用成本和延迟。

与此同时，鼠标操作场景要求高精度坐标定位（像素级）和低延迟（< 100ms），而 LLM 输出的文本格式坐标需要解析和转换，引入额外延迟和精度损失。

需要一种将"看"、"理解"、"执行"三种职责解耦的架构，使每一条通道都为各自的职责优化。

## 决策

采用**三通道架构**，将视觉信号处理分解为三条独立的数据通路：

```
┌─────────────────────────────────────────────────────────┐
│                      Screen Capture                      │
│                       (1280x720)                         │
└────────────┬──────────────┬──────────────────┬──────────┘
             │              │                  │
             ▼              ▼                  ▼
   ┌─────────────────┐ ┌──────────┐ ┌──────────────────┐
   │  Channel 1      │ │Channel 2 │ │  Channel 3       │
   │  Visual         │ │Conversa- │ │  Execution       │
   │  VLM            │ │tion      │ │  IconCache       │
   │  Qwen3-VL-2B    │ │LLM       │ │  L2+L3+L4        │
   │  ↓              │ │DeepSeek  │ │  ↓               │
   │  structured     │ │API       │ │  3-tier match    │
   │  persona prompt │ │          │ │  ↓               │
   │  ↓              │ │VLM desc  │ │  DPI-aware mouse │
   │  LLM input      │ │+ ASR     │ │                  │
   │                 │ │+ perso-  │ │                  │
   │                 │ │nality    │ │                  │
   └─────────────────┘ └──────────┘ └──────────────────┘
```

### Channel 1 — 视觉通道 (VLM → LLM)

- **模型**: Qwen3-VL-2B（本地 GPU），处理 1280x720 屏幕截图
- **Prompt 策略**: 使用结构化 persona prompt，指导 VLM 生成**紧凑的场景描述**而非完整 UI 树转储
- **输出**: 约 100 字符的浓缩自然语言场景描述（"用户正在浏览 Chrome 中的 GitHub 仓库页面，鼠标停留在 README 文件列表区域"）
- **目标 token 预算**: ~100 字符，约为以前全注入方案的 1/5 到 1/8
- **降级**: Qwen3-VL-2B 不可用时 → 截取屏幕但不生成描述（LLM 仅收到 ASR + Personality 信息）

### Channel 2 — 会话通道 (LLM)

- **模型**: DeepSeek API（云端）
- **输入构成**:
  - VLM 描述（Channel 1 输出，~100 chars）
  - ASR 转录文本（来自音频管道）
  - Personality + 情感上下文（来自人格层）
- **职责**: 生成自然语言回复，不处理坐标或 UI 元素数据
- **Token 节省**: 相比全注入方案，每轮对话减少 300-700 tokens

### Channel 3 — 执行通道 (IconCache)

- **缓存结构**: 三级缓存
  - **L2**: 高频图标（当前 session 已点击过的图标），LRU 淘汰
  - **L3**: 系统级图标（开始菜单、任务栏、系统托盘等持久化图标），TTL 淘汰
  - **L4**: 后台定期扫描的全屏图标索引，刷新周期可配置
- **匹配机制**: 3 级逐级匹配（L2 → L3 → L4），命中即返回坐标
- **坐标输出**: DPI 感知的像素坐标（考虑缩放因子），可直接传递给鼠标控制器
- **延迟目标**: 缓存命中时 < 10ms（无需 LLM 参与）
- **未命中降级**: 回退到 VLM 坐标估算或 OmniParser 实时检测

## 理由

1. **职责分离** — 三条通道对应三个完全不同的问题：描述场景、生成回复、定位交互目标。耦合在一个管道中导致每个任务都得到次优的 prompt 设计和 token 分配。

2. **Token 效率** — Channel 2（LLM会话）不需要结构化的 UI 数据。将场景压缩为 ~100 字符的自然语言描述后，DeepSeek API 调用成本降低 60-80%。

3. **延迟优化** — Channel 3（鼠标执行）要求低延迟。IconCache 的缓存命中可以在微秒级返回坐标，而 LLM 推理需要数百毫秒。分离执行通道意味着鼠标操作的延迟不依赖于 LLM 的响应时间。

4. **容错** — 一条通道的故障不影响其他通道。VLM 不可用时 LLM 仍可基于 ASR 对话；IconCache 未命中时可回退到 VLM 实时检测。

5. **可测试性** — 三条通道可以独立进行合约测试：VLM 输出验证、LLM 回复生成、IconCache 命中率测试，无需端到端依赖。

## 后果

### 正面
- LLM prompt 中的视觉描述从 ~500 字符减少到 ~100 字符，API 成本显著降低
- 鼠标点击操作不再等待 LLM 推理，IconCache 命中时延迟降低到 < 10ms
- VLM 故障不影响纯语音对话场景
- 每条通道可以独立优化（如 IconCache 可以单独扩展缓存策略）

### 负面（需接受）
- **VLM 信息损失** — 压缩到 ~100 字符的场景描述必然丢失细节。若 LLM 需要精确 UI 元素名称（如"点击第三行的 'Settings' 链接"），VLM 的压缩描述可能不够精确。需要设计 VLM prompt 确保关键交互元素的描述优先级最高。
- **缓存一致性** — IconCache 的 L2/L3/L4 三级缓存可能在 UI 变化后返回过期坐标（如窗口移动、图标重排）。需要有效的失效策略和 TTL 机制。
- **三通道协调** — 在涉及"看到按钮 → 理解功能 → 点击"的端到端流程中，Channel 1 和 Channel 3 的输出需要对齐。如果 VLM 描述的按钮坐标与 IconCache 返回的坐标不一致，鼠标可能点击错误位置。
- **冷启动** — 新应用程序或新 session 的 IconCache 为空，首次交互需要回退到 VLM 实时检测，延迟较高（~500ms 到 1s）。

### 实现要求
- Channel 1 的 VLM prompt 必须明确要求输出"紧凑的自然语言描述，限制在 100 字符以内"
- IconCache 的 DPI 感知坐标必须通过 `runtime_config` 读取屏幕缩放因子，不做硬编码
- 三级缓存必须分别记录 TTL 和命中率统计，以供缓存策略调优
- 三通道的对齐验证：Channel 1 描述中的交互目标坐标与 Channel 3 的缓存/检测坐标必须在执行前交叉校验
- VLM 降级时 Channel 2 必须能优雅处理空描述（仅用 ASR + Personality 生成回复）

### 测试要求
- 合约测试必须覆盖：
  1. Channel 1 VLM 输出长度 ≤ 100 字符
  2. Channel 2 在无 VLM 描述时仍能生成合理回复
  3. IconCache L2/L3/L4 逐级命中正确性
  4. IconCache 未命中时的 VLM 回退路径
  5. DPI 缩放因子不同时的坐标正确性
  6. 三通道坐标对齐校验（VLM 描述 vs IconCache 坐标的偏差阈值检查）
  7. IconCache TTL 过期后坐标失效验证

## 备选方案

### A: 全注入（原始方案）
将 OCR、OmniParser、YOLO 等所有结构化视觉数据直接拼入 LLM prompt。
- **优点**: 实现最简单，LLM 可获得最完整的视觉信息
- **缺点**: Token 膨胀严重（400-800 tokens/帧）；OCR 终端噪声增加幻觉风险；鼠标操作仍需 LLM 推理坐标，延迟高
- **结论**: 否决。Token 成本和延迟不可接受

### B: Window-Aware 结构化注入
将屏幕按窗口区域分割，只注入活动窗口的 UI 树，其他区域用轻量级标签代替。
- **优点**: 相比全注入减少了无关信息量
- **缺点**: 仍然保留结构化 UI 数据格式（非自然语言），prompt 内的语义密度低；窗口检测增加的预处理延迟；窗口边界检测错误可能导致注入错误的 UI 数据
- **结论**: 否决。仅做减量优化未解决根本问题——LLM 不需要结构化 UI 数据

### C: Florence-2 替代 VLM
用 Florence-2 模型替换 Qwen3-VL-2B 作为 Channel 1 的视觉模型。
- **优点**: Florence-2 的 caption 输出格式更适合结构化场景描述
- **缺点**: 额外 ~1.5GB VRAM 占用；低 VRAM 配置不可用；Florence-2 对中文场景描述的支持不如 Qwen3-VL
- **结论**: 否决。VRAM 成本高且中文本地化不足

### D: 纯 IconCache 无 VLM
省略 Channel 1（VLM），只依靠 IconCache 的图标匹配和 ASR 进行决策。
- **优点**: 零 VLM 推理开销，GPU 显存需求最低
- **缺点**: 无法感知 UI 布局变化和动态内容（如网页加载状态）；LLM 失去视觉上下文，描述能力大幅下降
- **结论**: 否决。视觉上下文对自然对话交互是不可或缺的
